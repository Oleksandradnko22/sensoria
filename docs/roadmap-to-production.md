# Sensoria — дорожная карта от прототипа к продакшену

## 0. Что есть сейчас

Весь проект — фронтенд-прототип: React + Vite + TypeScript + Tailwind, без бэкенда, без базы данных, без API, без реального сервера авторизации, без хранилища файлов. Всё, что выглядит как "данные" (программы, гайды, медитации, профили автора и участника, отзывы, транзакции, сообщения) — статические моки в `src/data/*.ts`. "Вход" — localStorage/sessionStorage с таймаутом, без проверки пароля против реальной базы. Модерация сообщений (`contactFilter.ts`) — чистая клиентская эвристика, которую любой обойдёт через devtools.

Это нормальная и правильная стадия для продукта — вся дизайн-логика, UX-потоки, тексты и структура кабинетов уже проверены и отрисованы. Дальше — превращение витрины в работающий сервис.

---

## 1. Бэкенд и данные — фундамент

Без этого ничего из следующих пунктов не заработает по-настоящему.

- **API-сервер** (Node/NestJS, или Django/FastAPI — выбор стека не UX-решение, можно брать любой удобный) поверх реальной **базы данных** (Postgres — разумный дефолт для такой модели данных: пользователи, контент, транзакции, отзывы).
- **Схема данных**: пользователи (с ролью author/participant, а не по localStorage), контент (программы/гайди/медитации) с версионированием и статусами публикации, покупки, отзывы, сообщения, транзакции.
- **Реальная авторизация**: хэширование паролей (bcrypt/argon2), выдача сессии через httpOnly-cookie или JWT с refresh-токеном — вместо самодельного localStorage-таймера. Текущая 3-часовая/закрытие-вкладки логика — хороший UX-слой, но должна опираться на серверную сессию, а не только на клиентское хранилище.
- **Email/телефон верификация** при регистрации (иначе аккаунт может завести кто угодно с любым email).

## 2. Платежи

Сейчас "покупка" курса нигде не списывает деньги — это просто переход между страницами.

- Интеграция платёжного провайдера (для Украины реалистично — LiqPay, Fondy, WayForPay; для международных карт — Stripe).
- Обработка успешной/неуспешной оплаты, чеки, возвраты (14-дневный возврат уже упомянут в FAQ участника — сейчас это просто текст, нужен реальный workflow).
- Хранение истории транзакций в БД, а не в моках `participantDashboard.ts`.

## 3. Контент — загрузка и хранение

Редактор курса автора сейчас даёт только инструкции "как снять обложку/видео", реальной загрузки файлов нет.

- Файловое хранилище (S3-совместимое: AWS S3, Cloudflare R2) для обложек и материалов.
- Видеохостинг/стриминг для уроков — either self-hosted (заметно дороже и сложнее) или встроить внешний плеер (Vimeo Pro, Mux, Bunny Stream) — дешевле и быстрее в разработке.
- Проверка загружаемых файлов (антивирус/размер/формат) перед публикацией.

## 4. Модерация сообщений — Phase 2

Уже задокументировано отдельно в `docs/messaging-moderation-architecture.md`, коротко:

- Серверная повторная проверка каждого сообщения (клиентскую проверку легко обойти).
- OCR для изображений (чтобы ловить контакты, присланные картинкой/скриншотом).
- Персистентный лог нарушений и эскалация (сейчас `recordViolation` живёт только в памяти вкладки и обнуляется при перезагрузке).
- Настраиваемые пороги риска для команды модерации, а не хардкод в коде.

## 5. Финансы и выплаты авторам

Сейчас "запит на дострокову виплату" — это `mailto:`-ссылка, открывающая почтовый клиент. Это честно объяснено как временное решение, но не масштабируется.

- Реальная интеграция с выплатным провайдером или банковским API для переводов авторам.
- Учёт налогов/ФОП-статуса (уже собираем эти данные в профиле — нужно, чтобы они реально использовались бухгалтерией/провайдером).
- Автоматический расчёт баланса на основе реальных транзакций, а не мок-чисел.

## 6. Уведомления

Сейчас никаких email/push-уведомлений нет вообще (ни о новом сообщении, ни о продаже, ни о выплате).

- Транзакционные письма (регистрация, покупка, новое сообщение, статус выплаты) через сервис вроде SendGrid/Postmark.
- Опционально — push/in-app уведомления, если это важно для вовлечённости.

## 7. Админка для команды Sensoria

Сейчас нет ни одного экрана для самой команды платформы — только кабинеты автора и участника.

- Панель модерации: очередь сообщений/контента, помеченных как REVIEW, с возможностью решения вручную.
- Управление пользователями (бан, верификация авторов, обработка жалоб).
- Обработка споров и возвратов.
- Базовая аналитика по всей платформе (не только "своя" аналитика автора).

## 8. Юридическая часть и комплаенс

Платформа про ментальное здоровье — здесь регуляторные риски выше, чем у обычного маркетплейса курсов.

- Условия использования, политика конфиденциальности, обработка персональных данных (GDPR — если есть аудитория из ЕС).
- Договор/оферта с авторами (сейчас упоминается "угода з автором" в тексте предупреждений — самого документа не существует).
- Дисклеймер: платформа не оказывает медицинскую/психиатрическую помощь, если кто-то из авторов не лицензированный специалист — стоит явно развести "поддержка/самопомощь" и "терапия".

## 9. Инфраструктура и эксплуатация

- Хостинг (Vercel/Netlify для фронтенда, отдельный сервер/контейнер для бэкенда), домен, SSL.
- CI/CD (сейчас проверка — это ручной `tsc -b`/`npm test`, нужно на каждый PR).
- Мониторинг ошибок (Sentry) и логов, аптайм-алерты.
- Security review перед продакшеном (особенно после появления реального бэкенда — XSS в отзывах/сообщениях, SQL-инъекции, rate limiting на логин).

## 10. Масштаб и рост (позже)

- SEO — сейчас это чистый SPA без серверного рендеринга, страницы курсов не индексируются поисковиками нормально. Нужен SSR/SSG (Next.js-подобный подход) для публичных страниц, если органический трафик важен.
- Реальная аналитика (не мок в `AuthorAnalytics`) — продуктовая аналитика (Amplitude/Mixpanel) + бизнес-метрики.
- Полнотекстовый поиск получше клиентской фильтрации, если каталог вырастет.

## Рекомендуемый порядок (MVP-путь)

Если нужно как можно быстрее дойти до "реального" продукта, а не идеального, порядок примерно такой:

1. Бэкенд + БД + реальная авторизация (без этого всё остальное — фикция).
2. Платежи (без них платформа не зарабатывает).
3. Загрузка контента + видеохостинг (без этого авторам нечего продавать).
4. Уведомления (иначе люди не узнают о продажах/сообщениях).
5. Модерация Phase 2 + админка — можно частично отложить, если запуск закрытый/с доверенными авторами на старте.
6. Выплаты через реального провайдера — можно первое время вручную (та же mailto-заявка), пока объёмы маленькие.
7. Юридическая часть — нужна до публичного запуска, не после.
8. SEO/масштаб — уже после того, как есть первые пользователи.

Что из этого приоритетнее для тебя — с бэкенда/авторизации, с платежей, или сперва хочешь юридически обвязать то, что уже есть?

## Addendum — работаем по этому порядку, все сервисы бесплатные

Два места, где "полностью бесплатно" технически невозможно, и это не выбор сервиса, а природа вещи:

- **Комиссия платёжного провайдера** — любой процессинг (Stripe/LiqPay/Fondy/WayForPay) берёт процент с транзакции, потому что через него реально идут деньги и карточные сети. Ежемесячной/абонентской платы можно избежать, а процента с оборота — нет ни у одного провайдера в мире.
- **Доменное имя** — реальный домен (`sensoria.com`/`.ua` и т.п.) стоит ~$10–15/год. Можно отложить и первое время работать на бесплатном сабдомене (`sensoria.vercel.app`).

Всё остальное на старте можно закрыть бесплатными тарифами:

| Задача | Сервис | Бесплатный лимит |
|---|---|---|
| БД + Auth + Storage | Supabase | Postgres, реальная авторизация, файловое хранилище — щедрый free tier |
| Хостинг фронтенда | Vercel / Netlify / Cloudflare Pages | Без ограничений по времени, с SSL |
| Email-уведомления | Resend / Brevo | Сотни писем в день бесплатно |
| Мониторинг ошибок | Sentry | Free tier достаточен для старта |
| CI/CD | GitHub Actions | Бесплатно для приватных репо (лимит минут) |
| Видеохостинг курсов | требует отдельного решения — см. ниже | — |

**Видео — отдельный случай.** Специализированные видеохостинги (Vimeo Pro, Mux, Bunny Stream) не бесплатны. Реально бесплатный вариант — загружать уроки как непубличные (unlisted) видео на YouTube и встраивать плеер: без хостинг-расходов, но с брендингом YouTube и без защиты от скачивания/расшаривания за пределами платформы. Это уже продуктовый компромисс, не инженерный — вернёмся к нему на этапе загрузки контента (Этап 3) и решим отдельно.

**Стек для Этапа 1 (бэкенд/БД/авторизация): Supabase.** Одним аккаунтом закрывает Postgres, реальную авторизацию (взамен нынешнего localStorage-таймера) и файловое хранилище — меньше всего кода писать с нуля, конвенциональный выбор для такого MVP.

### Что уже сделано в проекте

- Добавил `@supabase/supabase-js` в `package.json`.
- `.env.example` — куда положить URL и публичный ключ проекта.
- `src/lib/supabaseClient.ts` — обёртка клиента (пока без реальных ключей приложение продолжает работать на моках, не падает).
- `supabase/schema.sql` — черновая схема таблиц (профили автора/участника, контент, покупки, отзывы, сообщения) с базовыми правилами доступа (RLS) — готова вставить в SQL Editor Supabase.

### Что нужно от тебя, чтобы продолжить

1. Зарегистрировать бесплатный аккаунт на supabase.com и создать проект — это должна сделать ты сама, я не создаю аккаунты за пользователя.
2. Скопировать из настроек проекта (Project Settings → API) **Project URL** и **anon/public key** и прислать мне — этот ключ безопасно передавать, он не секретный (защита на уровне RLS-правил в базе, не на уровне ключа).
