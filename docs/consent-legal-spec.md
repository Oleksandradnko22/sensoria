Основание: [docs/legal/participant-agreement.md](legal/participant-agreement.md),

Актуальная платёжная модель — monobank split (`agentFeePercent`), продавец — автор, Sensoria получает только тариф.

| Есть сейчас | Проблема | Что делаем |

Одна редакция `LEGAL.edition = "1.0"` на все документы | Расширяем таблицу, вводим реестр документов с отдельной редакцией каждого |

| Возврат, отклонённый банком, — уведомление автору | Нет срока и последствия | 3 рабочих дня → приостановка новых продаж автора |

## 1. Реестр юридических документов

### 1.1. Таблица `legal_documents`

```sql
create table if not exists public.legal_documents (
  document text not null,               -- 'participant_agreement' | 'author_agreement' | 'terms' | 'privacy' | 'refunds'
  version text not null,                -- '1.0', '1.1'
  text_hash text not null,              -- sha256 опубликованного текста (hex)
  published_at timestamptz not null default now(),
  effective_from timestamptz not null,  -- для оферты автора: дата уведомления + 14 дней
  changes_summary text,                 -- 2–5 пунктов «что изменилось», показывается на экране согласия
  is_current boolean not null default false,
  primary key (document, version)
);
create unique index if not exists legal_documents_one_current on public.legal_documents (document) where is_current;
alter table public.legal_documents enable row level security;
create policy "anyone reads legal documents" on public.legal_documents for select using (true);
-- запись только через service role / админку владельца
```

- Хеш считается при сборке: скрипт `scripts/legal-hash.ts` берёт `SECTIONS` каждой страницы и выводит sha256. Владелец вставляет строку в `legal_documents` вместе с публикацией.
- Клиентская константа `LEGAL.edition` заменяется на `LEGAL.editions = { participant_agreement, author_agreement, terms, privacy, refunds }`. Сервер не доверяет клиенту: текущая редакция берётся только из `legal_documents`.

### 1.2. Расширение `legal_consents`

```sql
alter table public.legal_consents
  add column if not exists text_hash text,
  add column if not exists items jsonb not null default '[]'::jsonb,  -- [{ "key": "p1", "text": "…точный текст галочки…" }]
  add column if not exists context text not null default 'gate'
    check (context in ('registration', 'gate', 'checkout', 'author_paid', 'profile')),
  add column if not exists ip inet,
  add column if not exists user_agent text,
  add column if not exists withdrawn_at timestamptz;

alter table public.legal_consents drop constraint if exists legal_consents_document_check;
alter table public.legal_consents add constraint legal_consents_document_check check (document in (
  'terms', 'privacy', 'author_agreement', 'age_18',
  'participant_agreement', 'refunds', 'not_medical', 'health_data', 'marketing_email', 'author_paid_sales'
));
```

Старые записи не трогаем. Клиент больше не пишет в `legal_consents` напрямую: insert-политику для клиента удалить, запись только через RPC (п. 1.3).

### 1.3. RPC `accept_legal(p_items jsonb, p_context text)`

`security definer`, `search_path = public`.

Вход: массив `[{ document, version, items: [{key, text}] }]`.

Логика:
1. `auth.uid()` обязателен.
2. Для каждого документа `version` должна совпадать с `is_current` в `legal_documents`, иначе ошибка `stale_version`: клиент перезагружает экран.
3. IP берётся из `current_setting('request.headers', true)::json ->> 'x-forwarded-for'` (первый адрес), user agent — из `user-agent`. С клиента эти поля не принимаются.
4. `insert … on conflict (user_id, document, version) do nothing`. Если раньше согласие было отозвано (`withdrawn_at`), создаётся новая запись: уникальность заменить на частичный индекс `where withdrawn_at is null`.

### 1.4. RPC `withdraw_consent(p_document text)`

Только для `health_data` и `marketing_email`. Ставит `withdrawn_at = now()`. Для `health_data` дополнительно вызывает `purge_health_data(auth.uid())` (п. 4.3).

### 1.5. Функции проверки

```sql
-- true, если у пользователя есть действующее согласие на текущую редакцию документа
create or replace function public.has_current_consent(p_uid uuid, p_document text) returns boolean …
-- что пользователю нужно принять сейчас (для экрана согласия)
create or replace function public.missing_consents() returns table (document text, version text, changes_summary text) …
```

Наборы обязательных согласий:
- **Участник:** `participant_agreement`, `terms`, `refunds`, `privacy` (ознакомление), `age_18`, `not_medical`.
- **Автор:** `author_agreement`, `terms`, `privacy`, `age_18`. Пять галочек A1–A5 сохраняются в `items` одной записи `author_agreement`.
- **Автор с платными продажами:** дополнительно `author_paid_sales` (A6).
- `health_data` и `marketing_email` в обязательные не входят.

Для оферты автора: если текущая редакция ещё не вступила в силу (`effective_from > now()`), а предыдущую автор принимал, `has_current_consent` возвращает true и автор работает по старой редакции. После `effective_from` — false.

## 2. Экран согласия (gate)

### 2.1. Когда показывается
После **любого** появления сессии: вход по почте, Google, восстановление пароля, новое устройство, обновление страницы. Компонент `ConsentGate` подписывается на `onAuthStateChange` и вызывает `missing_consents()`. Если список не пуст, вместо кабинета открывается полноэкранный экран.

- Нет кнопки «пропустить» и закрытия по Esc или клику вне.
- Публичные страницы (каталог, юридические документы, «Допомога в кризі») доступны без экрана согласия. Gate закрывает только кабинет и действия.
- Доступны выход и «Видалити акаунт» (существующий поток `delete-account`).

### 2.2. Содержимое
- Заголовок по роли: «Угода учасника» или «Договір з автором».
- Если это новая редакция — блок «Що змінилося» из `changes_summary` и ссылки на полный текст.
- Галочки — дословно из `participant-agreement.md` / `author-consent.md`, ни одна не отмечена заранее.
- «Продовжити» активна, когда отмечены все обязательные.
- Ссылки на документы открываются в новой вкладке (как сейчас в `ConsentCheckbox`).
- Для автора дополнительно — баннер, если вышла новая редакция оферты, которая ещё не вступила в силу: «Нова редакція договору набирає чинності DD.MM. Прийняти зараз». Баннер не блокирует работу до `effective_from`.

### 2.3. Регистрация
Существующую галочку на форме регистрации и поле `consent_version` в метаданных **убрать**: согласие даётся на экране согласия сразу после первого входа. Триггер `handle_new_user()` больше не пишет согласия. Механизм `oauth_consent` в URL удалить.

### 2.4. Защита на сервере (gate нельзя обойти через адресную строку)
Без `has_current_consent` по всем обязательным документам роли база и edge-функции отказывают:

| Действие | Где проверять |
|---|---|
| Создание счёта на оплату | `monoCheckout` в `scripts/finance-handler.ts` / `supabase/functions/finance` — ошибка `consent_required` |
| Добавление бесплатного материала в кабинет | insert-политика `acquired_content` |
| Сообщения | `supabase/functions/send-message` |
| Комментарии, публикации, отзывы | insert-политики `content_comments`, таблиц из `feeds.sql`, `reviews`, `author_reviews` |
| Публикация материала автором | триггер или политика на `content` при переходе в `published` (для автора — `author_agreement`; при `price > 0` — также `author_paid_sales`) |
| Заявка на подключение к оплатам | `requestMonoConnection` — требует `author_paid_sales` |

Уже купленный доступ (чтение `acquired_content`, `purchases`, просмотр материалов) **не** блокируется: это прямо обещано в п. 12.1 угоды.

### 2.5. Одноразовый код при принятии оферты автором
Галочка без подписи — слабое доказательство для договора с деньгами. Закон «Про електронну комерцію» (ст. 12) считает электронную сделку подписанной электронной подписью, **одноразовым идентификатором** или аналогом собственноручной подписи; Верховный Суд признаёт договор, подписанный одноразовым идентификатором, равным письменному.
- После галочек A1–A5 (и отдельно A6) — шаг «Підтвердіть кодом»: 6-значный код на email автора, действует 10 минут, 5 попыток, повторная отправка не чаще раза в 60 с.
- Код генерирует и проверяет сервер (edge-функция `legal-otp`); в базе хранится только хеш кода.
- В запись `legal_consents` добавить `otp_verified_at timestamptz` и `otp_channel text` ('email'). Без проверенного кода `accept_legal` для `author_agreement` и `author_paid_sales` отклоняется (`otp_required`).
- Каждая новая редакция оферты подтверждается кодом заново.
- Для участника код не нужен: его согласие привязано к аккаунту с подтверждённой почтой или Google-входом, а каждая покупка дополнительно подтверждается оплатой картой с проверкой банка.

### 2.6. Защита от оспаривания «не усвідомлював свої дії» (ст. 225 ЦК)
- Экран согласия и оплата — без таймеров «осталось 5 минут», без предвыбранных галочек, без скрытых подписок и автопродлений.
- Если в последние 24 часа пользователь отметил кризисное состояние (тест, отметка настроения, обращение «Мені погано» в «Допомозі»), каталог и корзина **не показывают** промо-блоки и рекомендации платных материалов; вместо них — карточка с 112 и «Допомогою в кризі». Покупку по прямому желанию пользователя не блокируем.
- В `legal_consents` и `purchase_consents` хранить время, проведённое на экране (`viewed_ms`), и факт открытия текста документа (`opened_docs text[]`).

## 3. Оплата: продавец и немедленный доступ

### 3.1. Блок «Продавець» в корзине и на странице оплаты
- Данные из `author_mono_receivers` (`legal_name`, `ipn`) через RPC `seller_info(content_id)`. Только для `status = 'active'`.
- Показ: «Продавець: ФОП Іваненко Ірина Петрівна · код ••••1234» или «ТОВ "Назва" · ЄДРПОУ 12345678».
  - РНОКПП ФОП маскируем (последние 4 цифры), ЄДРПОУ ТОВ показываем полностью. Юрист подтверждает достаточность.
- Под блоком: «Sensoria — оператор платформи (технічні послуги)».

### 3.2. Галочка немедленного доступа
- Текст — дословно из `docs/legal/participant-agreement.md` (раздел «Галочка на сторінці оплати»), с подстановкой `{legal_name}`. Не отмечена заранее; без неё кнопка «Перейти до оплати» неактивна.
- **Тот же текст обязательно повторяется в подтверждении покупки**: в письме покупателю после успешной оплаты и в PDF-квитанции в «Оплати». Закон (п. 1 ч. 5 ст. 13 Закона № 1023-XII) связывает утрату права на расторжение с тем, что потребитель уведомлён об этом в подтверждении.
- Новая таблица (у `legal_consents` уникальность по редакции, а здесь нужна запись на каждый заказ):

```sql
create table if not exists public.purchase_consents (
  invoice_id uuid primary key references public.mono_invoices (id) on delete restrict,
  buyer_id uuid not null references auth.users (id) on delete set null,
  content_id uuid not null,
  seller_legal_name text not null,
  seller_code_masked text not null,
  consent_text text not null,
  ip inet,
  user_agent text,
  accepted_at timestamptz not null default now()
);
alter table public.purchase_consents enable row level security;
create policy "buyer reads own" on public.purchase_consents for select using (auth.uid() = buyer_id);
```

- `monoCheckout` принимает `payload.immediateAccess === true`, иначе ошибка `immediate_access_required`. Запись в `purchase_consents` делается **до** вызова `/api/merchant/invoice/create`, в той же ветке, где создаётся `mono_invoices`. IP и user agent — из заголовков запроса к edge-функции.
- Повторно использованный счёт (ветка `reused`) новую запись не создаёт.
- Записи не удаляются при закрытии аккаунта: это доказательство для чарджбека.

### 3.3. Квитанция покупателя
В PDF-квитанции в «Оплати» добавить строку «Продавець: …», пометку «Не є фіскальним чеком», ссылку на фискальный чек продавца (п. 3.4) и текст об отказе от права на расторжение (п. 3.2).

### 3.4. Фискальные чеки через ПРРО автора

Решение и обоснование — `docs/legal/accounting-model.md`, раздел 4. Чек выдаёт **автор** как продавец, на **полную цену**; Sensoria формирует его через API кассового сервиса от имени автора.

**Подключение автором** («Фінанси → Приймання оплат», после банковского подключения):
- Выбор сервиса ПРРО из поддерживаемых (на старте один, например Checkbox; адаптер под интерфейс `FiscalProvider`, чтобы добавить другие).
- Перед полем — чек-лист автора (`accounting-model.md`, 4.2): господарська одиниця «інтернет-магазин» (20-ОПП), ПРРО (1-ПРРО), печатка для ПРРО как ключ кассира (5-ПРРО).
- Автор вводит **токен доступа к кассе** (лицензионный ключ кассы + PIN кассира). Приватный ключ/КЭП автора Sensoria **не принимает**: поле загрузки ключевых файлов не делать. Токен хранить только на сервере, зашифрованным (Supabase Vault или `pgsodium`); в интерфейсе — «Підключено ••••last4».
- Пробный вызов API (статус кассы / смены). Успех → `author_fiscal.status = 'active'`.

```sql
create table if not exists public.author_fiscal (
  author_id uuid primary key references public.profiles (id) on delete restrict,
  provider text not null,                 -- 'checkbox' | …
  secret_ref text not null,               -- ссылка на секрет в Vault, не сам ключ
  cash_register_id text,
  status text not null default 'pending' check (status in ('pending', 'active', 'error', 'disabled')),
  last_error text,
  updated_at timestamptz not null default now()
);
create table if not exists public.fiscal_receipts (
  id uuid primary key default gen_random_uuid(),
  invoice_id uuid not null references public.mono_invoices (id) on delete restrict,
  author_id uuid not null,
  kind text not null check (kind in ('sale', 'return')),
  amount_kop bigint not null,
  provider_receipt_id text,
  fiscal_code text,
  receipt_url text,
  status text not null default 'pending' check (status in ('pending', 'done', 'failed')),
  attempts int not null default 0,
  last_error text,
  created_at timestamptz not null default now(),
  unique (invoice_id, kind, amount_kop)
);
```

**Логика:**
1. `monoCheckout` в live-режиме отказывает (`author_no_prro`), если `author_fiscal.status <> 'active'`, так же как без банковского подключения.
2. В `recordPaid` (успешная оплата) → поставить `fiscal_receipts(kind='sale', amount = полная цена)`. Отправка в фоне: смена открывается автоматически, если закрыта; позиция «Доступ до цифрового матеріалу “{title}”», цена, оплата «Картка», RRN/код авторизации и маска карты из данных monobank. Доступ покупателю **не** ждёт чека.
3. Повтор при ошибке в `runJobs` с нарастающей паузой — до конца **следующего рабочего дня** после оплаты (ДПС допускает фискализацию интернет-эквайринга не позднее следующего рабочего дня). Затем `failed` → оповещение автору и в админке («Чек не сформовано — сформуйте вручну у своєму ПРРО до кінця дня»).
4. Успешный возврат или проигранный чарджбек → `fiscal_receipts(kind='return')` на сумму возврата.
5. Чек отправляется покупателю на почту (силами сервиса ПРРО или нашим письмом со ссылкой) и показывается ссылкой в «Оплати».
6. Тестовый режим — тестовая касса сервиса.

### 3.5. Ежемесячный акт об услугах Sensoria
Модель — `accounting-model.md`, раздел 5; текст условия — оферта, Б13.
- Job 1-го числа: для каждого автора с продажами за прошлый месяц формируется PDF «Акт про надання послуг» (сумма = тариф за успешные оплаты месяца минус тариф за возвраты месяца) + приложение-перечень (дата, № заказа, цена, ставка, тариф, комиссия банка с доли автора, зачисление автору, возвраты).
- Подпись КЕП Sensoria: на старте владелец подписывает пакет в админке (выгрузка/загрузка подписанных файлов); позже — автоматизация через сервис КЕП.
- Кабинет автора, «Фінанси → Акти»: список, скачивание, кнопки «Прийняти» и «Заперечення» (текст). Без реакции 5 рабочих дней → статус «Прийнято (мовчазно)».
- Таблица `service_acts (id, author_id, period, amount_kop, pdf_path, signed_pdf_path, status 'draft'|'issued'|'accepted'|'accepted_silent'|'disputed', issued_at, decided_at, objection)`.

### 3.6. Налоговый доход автора в «Фінансах» и CSV
- Новый столбец «Дохід від продажу (для податкового обліку)» = цена продажи (не сумма зачисления).

## 5. Возвраты: отказ банка из-за нехватки средств у автора

### 5.1. Статусы
Добавить в `refund_requests` (или журнал попыток) состояние `bank_declined_insufficient`:

```
requested → approved → bank_pending → completed
                     ↘ bank_declined_insufficient → (повтор) bank_pending → completed
```

### 5.2. Логика
1. Ветка `mono_cancel_failed` в действии `refund` уже шлёт уведомление `REFUND_FAILED`. Дополнительно:
   - записать `refund_failures (id, payment_id, author_id, buyer_id, failed_at, deadline_at, resolved_at)`; `deadline_at` = +3 рабочих дня (сб, вс и праздники из таблицы `business_holidays` не считаются);
   - покупателю — уведомление и письмо: «Повернення схвалено. Банк ще не провів його; ми повідомимо, щойно кошти буде повернено». Статус в «Оплати» — «Повернення в обробці».
2. `runJobs`: если `deadline_at` прошёл и `resolved_at is null` → `author_details.sales_suspended_reason = 'refund_unfunded'`, `sales_suspended_at = now()`; уведомление автору; запись в `author_status_log`.
3. `monoCheckout`: при непустом `sales_suspended_reason` — ошибка «Продаж матеріалів автора тимчасово призупинено».
4. Каталог: материалы автора остаются видны, но кнопка покупки заменяется на «Тимчасово недоступно для купівлі». У купивших доступ не меняется.
5. Повтор возврата из админки (кнопка «Повторити повернення» в журнале). При успехе: `resolved_at`, снятие приостановки, если других незакрытых `refund_failures` нет; покупателю — «Кошти повернено».
6. Доступ к материалу у покупателя снимается **только** после успешного возврата (как сейчас в `revokePaidAccess`).

### 5.3. Чего не делать
- Не создавать запись в `author_debts`: долга перед Sensoria в этой модели нет.
- Не пытаться проверить баланс счёта автора.

## 9. Безопасность

- Все записи согласий — только через `security definer` RPC; у клиента нет insert, update и delete на `legal_consents` и `purchase_consents`.
- IP и user agent — только из заголовков на сервере.
- `purchase_consents`, `legal_consents`, `disputes` не удаляются каскадом при удалении профиля: `on delete set null` для `buyer_id` или перенос в `closed_participants` (как сейчас с покупками).
- Экспорт данных (`dataExport.ts`) включает согласия пользователя и его `purchase_consents`.
- Админские действия (повтор возврата, споры, просмотр переписки) пишутся в `finance_audit_log` с причиной.

## 11. Тестовые сценарии

1. Новый участник по почте → после подтверждения виден gate; без галочек 1–3 кнопка неактивна; после принятия — кабинет; в `legal_consents` есть `items` с точными текстами, IP и `text_hash`.
2. То же через Google — gate появляется, параметр `oauth_consent` не используется.
3. Пользователь без согласия вызывает `monoCheckout`, `send-message`, insert в `content_comments` напрямую через API → ошибка `consent_required`.
4. Публикуется `participant_agreement 1.1` → при следующем входе gate с «Що змінилося»; купленные материалы открываются по прямой ссылке и до принятия.
5. Участник без `health_data`: тест не сохраняется (ошибка из базы при прямом insert), материалы проходятся.
6. Отзыв `health_data` → данные из таблиц п. 4.1 удалены, экспорт до удаления работает.
7. Оплата без галочки немедленного доступа → кнопка неактивна; прямой вызов API → `immediate_access_required`; с галочкой — запись в `purchase_consents` до создания счёта.
8. Блок «Продавець» показывает маску РНОКПП для ФОП и полный ЄДРПОУ для ТОВ.
9. Возврат отклонён банком (мок `mono_cancel_failed`) → уведомления автору и покупателю; через 3 рабочих дня (с учётом выходных) продажи автора приостановлены; повтор успешен → приостановка снята, доступ покупателя снят, статус «Повернено».
10. Чарджбек открыт → доступ только к этому материалу приостановлен; `won` → восстановлен; `lost` → снят, запись `chargeback`.
11. Оферта 1.1 с `effective_from` через 14 дней → автор публикует по 1.0 до даты; после даты без принятия публикация и заявка на оплаты отклоняются, продажи уже опубликованного продолжаются.
12. Автор впервые ставит цену → галочка A6; без неё сохранение с `price > 0` и `requestMonoConnection` отклоняются базой.
13. Автор без активного ПРРО → `monoCheckout` в live возвращает `author_no_prro`; после подключения тестовой кассы оплата создаёт чек продажи на полную цену, возврат — чек возврата; при недоступности API чек переотправляется из `runJobs`, доступ покупателя открыт сразу.
14. Письмо-подтверждение и PDF-квитанция содержат текст об отказе от права на расторжение, совпадающий с текстом галочки.
15. 1-го числа формируются акты за прошлый месяц; сумма = тариф минус тариф возвратов; через 5 рабочих дней без реакции — «Прийнято (мовчазно)».
16. CSV автора содержит столбец «Дохід від продажу (для податкового обліку)» = цена.
17. Автор принимает оферту без кода → `otp_required`; с неверным кодом 5 раз → блок на 15 минут; с верным → `otp_verified_at` заполнено.
18. Пользователь с кризисной отметкой за последние 24 часа не видит промо платных материалов; прямая покупка работает.
19. `setSettings({mode: 'live'})` до релизов B и C отклоняется.

## 13. Критерии готовности

- Все сценарии раздела 11 проходят; юнит-тесты на подсчёт рабочих дней, маскирование кода, `missing_consents`.
- Ни одно защищённое действие не проходит без согласия при прямом вызове API, а не только через интерфейс.
- Тексты галочек в интерфейсе совпадают побуквенно с `docs/legal/*.md` (тест сравнивает строки).
- Публичные страницы не содержат старой модели (поиск по «резерв», «відклад», «утриман», «LiqPay», «Tranzzo», «25%» пуст).
- SQL-миграции идемпотентны (повторный запуск безопасен), лежат в `supabase/` отдельными файлами.
- `npm run build` и тесты проходят.
