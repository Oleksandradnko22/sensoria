# Лише ПриватБанк і monobank дають ФОП токен без договору

**Коротка відповідь.** Сьогодні (2 листопада 2026) лише два українські банки підтверджено дають ФОП самостійно, через власний кабінет, випустити токен для читання вхідних платежів: **ПриватБанк** (Автоклієнт API, лише опитування, призначення платежу є в полі `OSND`) і **monobank** (personal API, вебхук і виписка, поле `comment`). Жоден із цих двох шляхів не є «чистим» для платформи, яка зберігає токени багатьох авторів на своєму сервері. monobank прямо вимагає для такого сценарію корпоративний API із заявою й договором з банком і застерігає про санкції. ПриватБанк не забороняє, але радить не передавати токен третім особам, а письмового дозволу для комерційного сервісу ми не знайшли. ПУМБ має самообслуговну API-синхронізацію з Таксером (з 08.10.2026), але вона, найімовірніше, партнерська (двостороння домовленість Таксер–ПУМБ) і для іншої платформи не відтворюється автоматично. Для решти банків із вашого переліку ми не знайшли публічного API виписок для ФОП. Open banking за постановою НБУ № 80 формально покриває всіх, але платформа без власної авторизації НБУ як AISP читати рахунки через нього не може, а підтверджених небанківських TPP немає. Рекомендація для запуску: токен на боці автора (конектор або власний вебхук) для mono та Привата, завантаження виписки та підтвердження квитанцією для всіх інших, а з банками, що дають договір, домовлятися паралельно. Ключовий висновок: не залежіть від вхідного платежу на рахунок автора. Другий переказ (25%) надходить на рахунок самої платформи, і його ви бачите власним токеном без жодних ризиків.

## Що саме треба бачити і чому це звужує вибір

Сценарій Sensoria такий: покупець робить два перекази, 75% на ФОП автора й 25% на ФОП платформи, а зв'язує їх код у призначенні платежу. Тому для кожного банку важливі чотири речі. Перша: чи може ФОП-автор сам, без договору платформи з банком, видати доступ лише на читання. Друга: чи є вебхук, чи лише опитування. Третя: чи потрапляє призначення платежу (код) у дані виписки. Четверта: чи дозволяють умови банку, щоб токен лежав на сервері третьої сторони.

Рахунок самої платформи вирішує половину задачі. Платформа є ФОП (або юрособою) у конкретному банку й може випустити собі токен у ПриватБанку чи monobank як звичайний клієнт, без жодних договорів «для третіх осіб». Саме тому розумно будувати верифікацію так, щоб головним доказом був платіж 25% з кодом на рахунок платформи. Платіж 75% на рахунок автора тоді стає вторинною перевіркою. Це наш висновок з архітектури сценарію, а не з джерел. Його слабке місце в тому, що недобросовісний покупець може переказати лише 25%, а автору недоплатити. Тому повна гарантія оплати автору все одно потребує другого сигналу: токена автора, виписки або підтвердження автором.

## monobank: технічно найзручніший, юридично найжорсткіший

Personal API офіційно підтримує рахунки ФОП (тип `fop`, з IBAN). Токен у заголовку `X-Token` клієнт отримує сам на api.monobank.ua, він працює лише на читання. Виписка обмежена одним запитом на 60 секунд і періодом 31 доба + 1 година. Є вебхук `StatementItem`: на URL надсилається GET для перевірки, події йдуть POST-ом, за відсутності відповіді 200 протягом 5 секунд робляться повтори через 60 і 600 секунд, а після третьої невдачі функцію вимикають ([документація monobank](https://api.monobank.ua/docs/index.html); [OpenAPI-специфікація спільноти](https://raw.githubusercontent.com/andrew-demb/monobank-api-community-docs/main/specs/open_personal_api.json)). У елементі виписки для зарахування є сума в копійках, `comment` («коментар до переказу, уведений користувачем»), `counterName`, `counterIban`, `counterEdrpou` (лише для ФОП-рахунків) та `invoiceId` ([специфікація](https://raw.githubusercontent.com/andrew-demb/monobank-api-community-docs/main/specs/open_personal_api.json)).

Проблема в умовах. Документація каже: якщо ви хочете централізовано підключатися до API для надання послуг клієнтам, треба підключатися через API для провайдерів послуг, а програми, якими клієнт користується особисто і де «дані клієнта не проходять через вузли розробника», корпоративного API не потребують. Далі: «у разі виявлення експлуатації цього API в якості корпоративного, банк залишає за собою право накласти санкції на компанію» ([документація monobank](https://api.monobank.ua/docs/index.html)). Платформа, що зберігає токени авторів і сама приймає вебхуки, під це формулювання підпадає (це наше тлумачення, прямої цитати про «зберігання токенів» немає). Офіційний шлях: заявка через `POST /personal/auth/registration`, схвалення банком, підпис «Заяви про приєднання до корпоративного API», яка є невід'ємною частиною договору з АТ «Універсал Банк» і посилається на Моноправила для бізнесу ([corporate docs](https://api.monobank.ua/docs/corporate.html); [форма заяви](https://monobank.ua/pdf/dodatky_do_monopravyl/zaiava_pro_pryiednannia_do_korporatyvnoho_api_tov.pdf)). Автор тоді підтверджує доступ у застосунку mono (посилання діє 24 години), а платформа працює з `X-Request-Id`, а не з токеном. Це договір один на платформу, а не окремий на кожного автора, тобто вимогу «без договору на кожного автора» корпоративний API виконує, а вимогу «без жодного договору з банком» ні. Невідомо, чи потрібен платформі власний бізнес-рахунок у mono, скільки триває розгляд заяви і чи є плата: тарифи й Моноправила для бізнесу не вдалося прочитати.

Додаткові застереження. Для рахунків ФОП, до яких доступ надано бухгалтеру (`managedClients`), події вебхука не надсилаються. Один токен має один URL вебхука, тож ФОП, який уже підключив інший сервіс, перепише його (це висновок, прямо не підтверджено). Банк описує API як «особисту ініціативу» частини розробників, що підтримується у вільний час, без SLA ([community docs](https://github.com/andrew-demb/monobank-api-community-docs)). Найважливіше невідоме: чи потрапляє в `comment` саме призначення платежу IBAN-переказу з іншого банку, чи лише коментар з внутрішніх переказів mono→mono. Це треба перевірити тестовим платежем на реальний ФОП-рахунок.

## ПриватБанк: токен є, вебхука немає, дозволу на комерційне зберігання немає

ФОП створює в «Приват24 для бізнесу» застосунок «Автоклієнт» → API, вказує назву, за потреби IP-адреси і отримує токен. Послуга безкоштовна, для ФОП доступна на всіх тарифах ([ПриватБанк, Інтеграція](https://privatbank.ua/business/intehratsiya)). Токен можна обмежити вкладкою «Обмеження по сервісам» так, щоб він давав лише баланси й транзакції, без створення платежів ([опис API v3.0](https://docs.google.com/document/d/e/2PACX-1vTtKvGa3P4E-lDqLg3bHRF6Wi9S7GIjSMFEFxII5qQZBGxuTXs25hQNiUU1hMZQhOyx6BNvIZ1bVKSr/pub)). Усі методи є GET: `/transactions`, `/interim` (проміжні дані поточного дня, за замовчуванням 20, максимум 100 записів), `/final` (до 500) з пагінацією через `followId`. У відповіді призначення платежу лежить у `OSND`, контрагент у `AUT_CNTR_NAM/ACC/CRF`, напрям у `TRANTYPE` (C = кредит), унікальний ідентифікатор це REF+REFN ([опис API v3.0](https://docs.google.com/document/d/e/2PACX-1vTtKvGa3P4E-lDqLg3bHRF6Wi9S7GIjSMFEFxII5qQZBGxuTXs25hQNiUU1hMZQhOyx6BNvIZ1bVKSr/pub)). Слів webhook, callback чи push у документі немає, тож канал це лише опитування (висновок з відсутності, а не пряма заява банку). Числових лімітів запитів на хвилину немає, а під час регламенту (`work_balance=Y`) запитувати не можна. ФОП може будь-коли вимкнути доступ: тоді API повертає 403.

Юридично документація каже: «Не передавайте токен третім особам. Якщо плануєте зберігати чи використовувати токен не на своєму сервері або в застосунку, ознайомтеся з їхньою політикою конфіденційності» ([опис API v3.0](https://docs.google.com/document/d/e/2PACX-1vTtKvGa3P4E-lDqLg3bHRF6Wi9S7GIjSMFEFxII5qQZBGxuTXs25hQNiUU1hMZQhOyx6BNvIZ1bVKSr/pub)). Це не заборона, а перекладання відповідальності на клієнта. Про сторонні сервіси банк на сторінці інтеграцій відсилає до їхньої підтримки (Bookkeeper, Dilovod, Дебет Плюс, MASTER:Бухгалтерія), а публічних умов, що прямо дозволяють чи забороняють комерційний агрегатор без договору, ми не знайшли. Банк заявляє, що понад 85 000 бізнес-клієнтів використовують його відкриті API-сервіси ([ПриватБанк, 25.08.2026](https://privatbank.ua/news/2026/8/25/cifrova-ekosistema-dlya-ukrajinskogo-biznesu-vzhe-85-000-biznes-kliyentiv-vikoristovuyut-vidkriti-api-servisi-privatbanku)), але текст новини ми не змогли прочитати. Практичний висновок: ризик нижчий, ніж у mono (немає прямої санкційної норми), проте письмове підтвердження від банку потрібне. Формат IBAN у полі контрагента в прикладі документації старий, тож його теж треба перевірити.

Окремо: «Відкрита виписка» ПриватБанку для платформи не підходить, бо не містить ні призначення платежу, ні IBAN контрагента ([ПриватБанк](https://privatbank.ua/business/openstatement)).

## Інші банки: від токена в Укргазбанку до порожнечі

Нижче зведено лише те, що підтверджено джерелами. «Не знайдено» означає, що в обмеженому пошуку доказів немає, а не те, що API відсутнє.

| Банк | Механізм доступу до виписки ФОП | Автоматичний доступ без окремого договору платформи | Вебхук | Призначення платежу в даних | Статус перевірки |
|---|---|---|---|---|---|
| monobank | Personal API: токен клієнта, виписка + вебхук | Технічно так, але умови вимагають корпоративний API для сервісів із токенами клієнтів; корпоративний = договір платформи з банком | Так (`StatementItem`); для managedClients ні | Поле `comment`; відповідність призначенню IBAN-переказу не підтверджена | Документація прочитана; поведінка не перевірена |
| ПриватБанк | Автоклієнт API: токен ФОП, лише опитування | Так, токен виписує ФОП; банк радить не передавати його третім особам | Не знайдено | Так, `OSND` | Документація прочитана; умови користування в кабінеті не бачили |
| ПУМБ | API-синхронізація з Таксером (з 08.10.2026), згода ФОП у кабінеті Таксера | Не для довільної платформи: ймовірно, партнерська інтеграція | Не відомо | Не відомо | Лише прес-реліз |
| Укргазбанк | `my.ukrgasbank.com/api`, токен в заголовку Authorization (за описом платного Odoo-модуля) | Не підтверджено; де ФОП бере токен, невідомо | Ні, у модулі опитування | У модулі поля контрагента й суми; призначення не підтверджено | Вторинне джерело |

| Ощадбанк, OTP, Sense Bank | Open banking на API KIT (Open API HUB), з 01.08.2026 | Лише через TPP з авторизацією НБУ; ФОП-покриття не підтверджено | Не відомо | Не відомо | Повідомлення в пресі; документації немає |
| Укрсиббанк | Авторизація НБУ як AISP/PISP (червень 2026) | Це роль TPP, а не доказ, що банк віддає дані сторонам | Не відомо | Не відомо | Не знайдено API |
| Креді Агріколь, МТБ | «Завершують впровадження» open banking (05.08.2026) | Не відомо | Не відомо | Не відомо | Дата запуску не підтверджена |

| Універсал (не mono) | Не знайдено | Не відомо | Не відомо | Не відомо | Немає даних |

Джерела до таблиці: для ПУМБ ([Finance.ua, 08.10.2026](https://news.finance.ua/ua/pumb-i-takser-zapustyly-avtomatychnu-synhronizaciyu-vypysky-dlya-fop-menshe-rutyny-bil-she-chasu-na-biznes); [Banker.ua](https://banker.ua/uk/pumb-takser-zapustili-avtomatichnu-sinhronizaciyu-2/)); для Укргазбанку ([Odoo Apps, Kitworks](https://apps.odoo.com/apps/modules/18.0/kw_bank_statement_ukrgasbank_api)); для Укрексімбанку ([форма заяви](https://www.eximb.com/assets/files/download/zayava-pro-pidkluchennya-do-api-sg-13-06-2025.pdf)); для Ощадбанку, OTP, Sense, Креді Агріколь і МТБ ([Мінфін, 05.08.2026](https://minfin.com.ua/2026/08/05/179093822/)); для Sense Bank також ([Інтерфакс-Україна, 28.07.2026](https://interfax.com.ua/news/press-release/1188606.html)); для Укрсиббанку ([Мінфін, 25.06.2026](https://minfin.com.ua/ua/amp/2026/06/25/176515986/)). Для Райффайзена сторонні модулі працюють із DBF ([Odoo Apps](https://apps.odoo.com/apps/modules/18.0/kw_bank_statement_ukrgasbank_api)).

Два застереження до таблиці. По-перше, PUMB-Таксер це прес-реліз банку, тобто рекламний матеріал: механізм авторизації, вебхук чи опитування, ліміти й вартість не розкриті. Комерційна умова партнерства (знижка 40% на Таксер, безкоштовне обслуговування рахунку для нових клієнтів за партнерським посиланням) вказує на двосторонню домовленість. По-друге, для Ощадбанку, OTP і Sense один читач у коментарях під статтею Мінфіну повідомляв, що застосунок ПУМБ видає помилку «цей банк не обмінюється даними». Це анекдотичний, неперевірений відгук, але він застерігає не вважати «заявлено» тим самим, що «працює».

Для шести найменших банків зі списку (А-Банк, Власний Рахунок, Bank Vostok, Мотор-Банк, Таскомбанк, Idea Bank), а також Кредобанку, Альянсу та інших дослідження нічого не дало: ні документації, ні типу авторизації, ні сторонніх інтеграцій. Відсутність доказів не доводить відсутності API, але закладати такі банки в запуск без підтвердження від банку не можна. Побічний орієнтир: Таксер, за власним описом, автоматично синхронізує лише monobank і ПриватБанк (плюс ПУМБ відтепер), а для решти пропонує універсальний шаблон файлу ([Таксер](https://taxer.ua/uk/features)). Це зі зведення пошуку, сторінка не відрендерилась. Те саме робить ПриватБанк: його «Книга обліку доходів» приймає виписки з будь-яких банків як завантажений файл ([ПриватБанк, 28.04.2026](https://privatbank.ua/news/2026/4/28/privatbank-sprostiv-podatkovu-zvitnist-dlya-biznesu-teper-vipiski-z-usih-bankiv-mozhna-zibrati-v-odnomu-misci)). Тобто навіть зрілі сервіси на ринку покладаються на файли для довгого хвоста банків.

## Open banking (постанова НБУ № 80): правильний довгостроковий шлях, але не для запуску

Постанова № 80 від 25.07.2025 діє з 01.08.2025. Вона запроваджує PSD2-подібну модель: банки (ASPSP), сторонні надавачі (AISP/PISP) з авторизацією НБУ, технологічні оператори, доступ лише за згодою користувача з посиленою автентифікацією; користувачем може бути фізична або юридична особа ([НБУ](https://bank.gov.ua/en/payments/open-banking); [Asters](https://www.asterslaw.com/press_center/legal_alerts/open_banking_to_launch_in_ukraine_on_1_august_2025/)). Для платформи є два блокери. Перший: AISP потребує авторизації НБУ за Положенням № 81 і кваліфікованого сертифіката відкритого банкінгу ([НБУ](https://bank.gov.ua/en/payments/open-banking)); у червні 2026 такі авторизації мали лише ПриватБанк, ПУМБ і Укрсиббанк, а небанківських TPP ми не знайшли ([Мінфін, 25.06.2026](https://minfin.com.ua/ua/amp/2026/06/25/176515986/)). Другий: базові (безкоштовні, без договору) інтерфейси мінімальні. У ПриватБанку це згода на один рахунок до 90 діб, не більше 4 викликів на добу без участі користувача і історія за 31 добу ([ПриватБанк, open banking для розробників](https://privatbank.ua/handbook/openbanking-for-developers)). Сповіщення про операції та повна історія віднесені до комерційних інтерфейсів, що потребують договору й можуть бути платними ([Asters](https://www.asterslaw.com/press_center/legal_alerts/open_banking_to_launch_in_ukraine_on_1_august_2025/)). Тобто «без договору з кожним банком» у режимі, придатному для моніторингу платежів, open banking сьогодні не дає.

Позитивний бік: Мінфін пише, що банки на API KIT можна підключати «по єдиній специфікації без окремих домовленостей з кожним банком», і називає серед сценаріїв автоматизований облік для ФОП ([Мінфін, 05.08.2026](https://minfin.com.ua/2026/08/05/179093822/)). Є й агрегатори: Open API Hub від ЄМА (API Connect) і оператор UPC з майбутнім маршрутизатором OneLinkUA ([ЄМА](https://ema.com.ua/news/asotsiatsiia-iema-ta-ukraino-shvejtsarska-kompaniia-gd-next-prezentuvaly-open-api-hub-tekhnolohichnyj-fundament-dlia-rozvytku-vidkrytoho-bankinhu-v-ukraini); [Інтерфакс-Україна](https://interfax.com.ua/news/economic/1142055.html)). Невідомо: чи віддають API поле призначення платежу (специфікацій не читали), вартість і строк авторизації НБУ, ціни агрегаторів, чи доступний режим «через авторизованого TPP як агент». Загальний висновок джерел: open banking це стратегічний шар на 2027+, а не рішення для запуску. Побічне спостереження: 22.10.2026 ПриватБанк запустив у «Приват24 для бізнесу» додавання рахунків інших банків, і там поки доступний лише monobank. Це напрямок «ПриватБанк читає чужі рахунки», а не «сторонній читає ПриватБанк», тож для Sensoria це не канал ([Дебет-Кредит, 22.10.2026](https://news.dtkt.ua/finance/bank-system/115800-privatbank-zapustiv-vidkritii-banking-dlia-fop-ta-fizosib)).

## Токени на сервері платформи чи на боці автора: правовий ризик і вибір

Зберігання токенів авторів на сервері Sensoria несе три різні ризики. Перший, договірний щодо банку: у monobank це пряма підстава для санкцій за умовами документації, у ПриватБанку це непряме застереження без явної заборони. Другий, відповідальності перед автором: токен ПриватБанку може бути звужений до читання, але витік токена розкриває автору фінансові дані, а ФОП за цим застереженням банку сам відповідає за вибір сервісу. Третій, захист персональних даних: контрагенти в виписках це платники, тобто треті особи, чиї дані платформа почне обробляти; це питання для юриста, у джерелах не розглянуте. Окремо слід перевірити, чи не є передача токена порушенням умов самого ФОП перед банком (умови користування в кабінеті ми не читали).

Альтернатива, яку сам monobank визнає допустимою, це програма, якою клієнт користується особисто, де «дані клієнта не проходять через вузли розробника». На практиці це маленький конектор, який автор запускає у себе (скрипт, контейнер чи простий застосунок), тримає токен і вебхук-приймач на власній інфраструктурі й передає платформі лише підписане повідомлення «надійшов платіж з кодом X на суму Y». Тут платформа не отримує ні токена, ні повної виписки. Мінуси очевидні: автор технічно має щось розгортати, довіра до повідомлення тримається на підписі конектора, а не на банку, і такий конектор можна підробити. Проміжний варіант, який ми вважаємо практичним, це хмарний конектор, що працює на токені автора, але не належить платформі (наприклад, прості сервіси на кшталт serverless-шаблону, який автор розгортає у власному акаунті). Він зменшує бар'єр, зберігаючи принцип «токен не в Sensoria». Юридичну прийнятність такої схеми з боку mono теж слід підтвердити письмово.

Третя альтернатива зовсім не потребує токена: автор завантажує виписку (CSV, XLS, 1С або DBF) або підтверджує отримання. Вона працює з будь-яким банком і є стандартним запасним варіантом ринку (Таксер, «Книга обліку доходів» ПриватБанку). Мінуси: затримка, ручна дія автора, можливість підробити файл. Підробка частково знімається, якщо платіж 25% на рахунок платформи перевіряється автоматично, а виписка автора потрібна лише як додатковий доказ.

## Рекомендований порядок банків для запуску і запасний варіант

Перший етап (запуск). Рахунок платформи в ПриватБанку або monobank з власним токеном: це головний автоматичний сигнал по платежу 25% з кодом. Для авторів: ПриватБанк через токен лише на читання (опитування `interim`, звіряння за REF+REFN), але з письмовим підтвердженням банку про допустимість; monobank через токен і вебхук на боці автора (конектор), а корпоративний API подати на розгляд паралельно. Порядок обґрунтований тим, що ці два банки єдині мають підтверджений публічний механізм і зрілу документацію, а за наявними даними Таксер синхронізує автоматично лише їх. Обсяг ринку цих банків серед ФОП ми не мали з джерел, тож цей пріоритет спирається на доступність механізму, а не на частку ринку.

Другий етап. Корпоративний API monobank (якщо банк погодить і умови прийнятні), що прибирає вимогу про конектор. Далі ПУМБ, але лише через пряму розмову з банком про партнерство або через авторизованого TPP, бо готового самообслуговного шляху поза Таксером не видно. Укргазбанк і Укрексімбанк варто розглядати тільки якщо серед авторів виявиться помітна кількість клієнтів цих банків. Для Укргазбанку є токен-API, для Укрексімбанку потрібна заява клієнта й оплата за тарифом, що важко вимагати від кожного автора.

Третій етап (2027+). Open banking: власна авторизація НБУ як AISP або партнерство з авторизованим TPP, через агрегатор (Open API Hub, UPC). Це розумно, лише коли виясниться, що API віддають призначення платежу, що покриваються рахунки ФОП і які ціни комерційних інтерфейсів. Ощадбанк, OTP, Sense, Креді Агріколь, МТБ, Укрсиббанк, Райффайзен, А-Банк та менші банки тримати у запасному варіанті, доки банки письмово не підтвердять доступ.

Запасний варіант для всіх інших: автор завантажує виписку за період або фотографію/PDF платіжного доручення, а платформа переводить угоду в статус «очікує підтвердження», і автор натискає «отримав». Щоб не отримувати хибних підтверджень, платіж 25% на рахунок платформи має бути перевірений автоматично, а підтвердження автора потрібне лише для частки 75%. Для спорів зручно зберігати файл виписки та хеш. Окремо зазначимо: у цьому звіті не оцінювалася відповідність такої схеми податковому й валютному регулюванню та правилам фінансового моніторингу (розподіл платежу покупця між двома ФОП), хоча це питання варто винести юристу.

## Що треба перевірити безпосередньо в банках

Для monobank: чи потрібен платформі власний бізнес-рахунок для корпоративного API, строк розгляду, плата, зміст дозволів `permission` (літери p, s, f, j не розшифровані), текст Моноправил для бізнесу про «Уповноваженого отримувача інформації», чи доступний `corp-api.monobank.ua` ФОП, і чи дозволений сценарій «конектор автора» в письмовому вигляді. Тестовий платіж з іншого банку на ФОП-IBAN у mono: що саме потрапляє в `comment`, `counterIban` та `invoiceId`, з якою затримкою приходить вебхук і чи надходять події для зарахувань через еквайринг.

Для ПриватБанку: письмова відповідь підтримки Приват24 для бізнесу (3700) чи менеджера, чи допускає банк комерційний сервіс, що зберігає токени ФОП без окремого договору; чи є партнерська програма для SaaS; точні умови користування, які ФОП приймає при створенні токена; числові ліміти запитів; чи є механізм push; чи розділ «Інтеграція» доступний у мобільному Приват24 для ФОП, що відкрили рахунок у застосунку; формат контрагента (IBAN чи старий номер рахунку); актуальність старого P24 API; текст новини від 25.08.2026 про відкриті API-сервіси.

Для ПУМБ: чи розкрита партнерська модель Таксера доступна іншим платформам, і якою є технічна схема (OAuth, вебхук чи опитування, поля виписки). Для Укргазбанку: де ФОП отримує токен, офіційна документація, ліміти, чи є призначення платежу. Для Укрексімбанку: специфікація сервісного API і тарифи. Для Ощадбанку, OTP, Sense, Креді Агріколь, МТБ, Укрсиббанку: чи їхній open banking реально працює для рахунків ФОП, чи є сповіщення про операції, чи віддається призначення платежу, умови комерційних інтерфейсів. Для Райффайзена, Універсал (не mono), А-Банку, Власного Рахунку, Bank Vostok, Мотор-Банку, Таскомбанку, Idea Bank: чи є будь-який API або автоматичний обмін, і лише потім файл. Для НБУ та юристів: вартість і строк авторизації AISP, обов'язкове страхування (проєктна цифра 150 тис. євро не підтверджена чинним текстом), чи можна працювати як агент авторизованого TPP, текст постанов № 80 і № 81 повністю, повний реєстр банків із живим API.

## Висновок

Головна несподіванка цього дослідження в тому, що питання «який банк дає токен» менш важливе, ніж питання «хто його тримає». Технічно доступ є в двох банків, але дозвіл тримати такі токени централізовано є лише в monobank, і то через договір. Тому найстійкіша архітектура для запуску така: платформа довіряє власному рахунку, де платіж 25% з кодом видно без чужих токенів, а решту підтверджує або конектор на боці автора, або файл, або натискання «отримав». Тоді відсутність API у більшості банків не блокує продукт, а лише впливає на швидкість підтвердження.

Друга думка: ринок рухається до моделі «банк–партнер–ФОП» (Таксер–ПУМБ), а не до відкритої моделі токена. Якщо цей напрям триватиме, шлях Sensoria до автоматичного підтвердження в довгому хвості банків лежить або через підписання партнерських угод з окремими банками, або через авторизацію НБУ та агрегатор, і обидва шляхи потребують часу й коштів, тому їх варто закладати в план 2027 року, а не очікувати на запуску.
